# Стандарты документации

## Назначение

Документация — инженерный результат и долговременная память OSIP. Markdown и текстовые исходники диаграмм в Git авторитетны. MkDocs Material и GitHub Pages создают удобное сгенерированное представление; сгенерированные страницы никогда не редактируются как отдельный source.

## Канонические расположения

| Артефакт | Каноническое место | Правило |
| --- | --- | --- |
| Основа, стратегия, спецификации, руководства | `docs/` | Одна тема — одна каноническая страница; вместо копий используются ссылки. |
| Архитектурные решения | `adr/` | Последовательная нумерация; принятые записи заменяются, а не переписываются. |
| Доказательства и оценка исследований | `research/` | Указывать вопрос, источники, метод, выводы, ограничения и итоговое решение. |
| Диаграммы C4 и инфраструктуры | `diagrams/*.puml` | Исходник PlantUML версионируется с документом, который на него ссылается. |
| Диаграммы процессов, последовательностей, состояний и journey | Mermaid-блоки Markdown или `diagrams/*.mmd` | Текстовый source проверяем и имеет указанного владельца. |
| Выбор оборудования | `bom/` | Указывать модель, совместимость, жизненный цикл и ссылки на решения. |
| Развёртывание и эксплуатация | `deployment/` | Сочетать исполняемые артефакты с понятными runbooks. |

## Жизненный цикл

Обычная последовательность: идея → архитектура → ADR (если существенно) → спецификация → реализация → тесты и эксплуатационные доказательства. Pull request, меняющий поведение системы, в том же изменении при необходимости обновляет спецификацию, диаграмму, влияние на ADR и runbook.

## Требования к тексту

У документа есть понятные title, purpose, статус при необходимости, scope и ссылки на связанные решения. Факты отделяются от предложений и допущений. Требования используют наблюдаемый язык: «должна продолжать локальную работу при потере WAN», а не «должна быть надёжной».

Не создавайте placeholder-страницы для решения, готового к документированию. Если тема действительно не решена, создайте краткую запись вопроса с владельцем, нужными доказательствами, сроком или триггером решения и ссылкой на ADR либо исследование.

## Диаграммы

PlantUML используется для C4, развёртывания, компонентов, инфраструктуры и сети. Mermaid — для flows, sequences, states, journeys, timelines и простых связей в Markdown. Диаграммы указывают scope и source file и не должны дублировать расходящиеся копии архитектурной модели.

## Языковая политика

Английский — канонический язык спецификаций платформы и ADR, чтобы репозиторий был широко применим. У каждой английской страницы документации есть структурно эквивалентный русский перевод. Русские страницы ссылаются на английскую каноническую запись, содержат статус/дату перевода и обновляются в том же изменении, что и их английский источник. CI проверяет парные пути файлов и актуальный статус перевода; review проверяет точность переданного смысла.

## Чек-лист ревью

- Это каноническое место для факта?
- Требует ли изменение ADR или обновления его последствий?
- Явно ли отражены допущения, эффекты безопасности/конфиденциальности и эксплуатации?
- Разрешаются ли связанные диаграммы и навигация?
- Обновлён ли русский перевод вместе с английским источником, с теми же решениями, диаграммами и ссылками?
- Оставляет ли изменение будущему инсталлятору или оператору достаточно доказательств для понимания?
