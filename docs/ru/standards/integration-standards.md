# Стандарты интеграций

## Назначение

Эти стандарты сохраняют интеграции OSIP независимыми от вендоров и развиваемыми. Они относятся к HTTP API, MQTT, адаптерам устройств, gateway и будущим транспортам. Transport topic или payload вендора никогда не становится недокументированным публичным контрактом.

## Правила контрактов

Каждая опубликованная команда, событие, проекция состояния или query OSIP объявляет владельца, semantic version, идентификатор, источник, время возникновения, данные correlation/causation, классификацию конфиденциальности, схему и семантику отказа. Обратно совместимые изменения аддитивны; несовместимые создают новую версию и план миграции. Потребители должны переносить неизвестные добавочные поля и дублирующую доставку.

## Граница MQTT

MQTT topics — маршрутизация транспорта, а не бизнес-смысл. Начальное соглашение: `osip/<environment>/<classification>/<domain>/<subject>`, где classification — `event`, `command`, `state`, `diagnostic` или `integration`. QoS, retention, expiry и last-will выбираются по контракту. Retained messages требуют health источника и timestamp; они не доказывают текущую достижимость физического устройства.

Raw topics адаптеров остаются в integration namespace. Ingress-адаптер проверяет credentials и payload, сопоставляет identity, нормализует поддерживаемые возможность и публикует контракты OSIP с отдельными credentials. Потребители ядра не должны управлять устройствами через raw topics адаптера.

## Identity

OSIP назначает стабильные доменные ID, например `device_id`, `space_id` и `integration_id`. Серийные номера вендоров, IEEE/EUI-64, короткие радиоадреса, friendly names, endpoints и облачные идентификаторы — интеграционные атрибуты с источником и timestamp жизненного цикла. Замена, слияние или вывод из эксплуатации — явная операция жизненного цикла; повторное использование идентификатора запрещено.

## API и совместимость

Синхронные API открывают явные границы resource, command и query. Они аутентифицируют каждого caller, авторизуют по наименьшим привилегиям, валидируют ввод, возвращают типизированные ошибки и выдают audit-friendly correlation ID. Описания API — версионированные source artefacts; event contracts используют тот же словарь и правила identity. Новые адаптеры доказывают соответствие контрактам fixtures и integration tests до получения поддержки.

## Именование и релизы

Имена пишутся в нижнем регистре, стабильны и исходят из домена. Не используйте имена вендоров в общих контрактах. Документы, схемы, диаграммы и исполняемая конфигурация версионируются вместе, когда изменение меняет наблюдаемое поведение. Релиз отмечает изменения контрактов, миграцию, совместимые версии адаптеров, эксплуатационное влияние и границу rollback.
