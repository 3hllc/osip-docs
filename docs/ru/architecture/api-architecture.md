# Архитектура API

## Типы интерфейсов

OSIP использует разные контракты для разных задач взаимодействия: события для асинхронных фактов, команды для запрошенных изменений, запросы для текущих и исторических проекций, интерфейсы конфигурации для рассмотренных долговечных изменений и интерфейсы человека или инсталлятора для контролируемых операций. UI является клиентом этих границ, а не привилегированным альтернативным API.

## Владение контрактом и версионирование

У каждого опубликованного интерфейса есть владелец, аудитория, метод аутентификации, область авторизации, классификация данных, политика совместимости и тестовый fixture. Внешние HTTP-интерфейсы используют версионированные OpenAPI-контракты, когда это выбрано; event-контракты следуют Event Model. Несовместимые изменения получают новый major-контракт и объявленный путь миграции. Недокументированные endpoints, прямой доступ к базе данных и общие credentials брокера не являются поддерживаемыми API интеграции.

## Авторизация

Аутентификация устанавливает идентичность человека, службы, устройства или инструмента инсталлятора. Авторизация оценивает запрошенное действие относительно роли, области инсталляции, ресурса, policy безопасности и, при необходимости, одобрения жителя. Административная конфигурация, команды устройствам и мониторинг только для чтения являются отдельными разрешениями. Межсервисные запросы используют identity, ограниченные назначением, а не унаследованный токен администратора-человека.

## Совместимость и наблюдаемость

API-ответы и события содержат correlation identifiers и осмысленные ошибки без утечки секретов. Deprecation объявляется в контракте и измеряется до удаления. Тесты контрактов покрывают авторизацию, валидацию, идемпотентность, поведение ошибок и обратную совместимость; эксплуатационная telemetry сообщает об использовании версий и неуспешных запросах.
