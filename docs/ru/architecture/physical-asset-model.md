# Модель физических активов

## Назначение

OSIP управляет физической реальностью, а не каталогом интеграций. Сущность Home Assistant, MQTT-топик, объект BACnet, групповой адрес KNX или идентификатор производителя — это свидетельство об активе, но никогда не первичная идентичность управляемой сущности. Эта спецификация определяет устойчивую пространственную иерархию, идентичность активов, связи, возможности и правила ввода в эксплуатацию, которые делают приложения переносимыми между провайдерами интеграций.

## Пространственная иерархия и граф

Иерархия вложенности задаёт рабочую область каждой записи. Не каждое развёртывание обязано использовать каждый уровень, но дочерний объект не может принадлежать двум родителям одного типа вложенности без явно задокументированного исключения.

```text
Site
└── Building
    └── Floor
        └── Space
            ├── Room
            ├── Corridor
            └── Zone
```

Zones — это семантические или операционные области; они могут пересекать границы комнат. Дерево вложенности дополняется типизированным графом отношений. Например: `HVAC-17 обслуживает Room-204`, `Door-12 соединяет Room-204 и Corridor-2`, `Sensor-81 измеряет-температуру-в Room-204`, `Room-204 принадлежит Fire-Zone-F2`. Граф не позволяет кодировать отношения безопасности, доступа, обслуживания, смежности или наблюдения в названии комнаты либо теге dashboard.

## Идентичность актива

При вводе в эксплуатацию актив получает стабильный OSIP `asset_id`, например `asset:hotel-001:hvac-17`. В его запись входят область объекта, тип, жизненный цикл, отношения, возможности, происхождение и история проверенных привязок. Идентичность не переиздаётся при смене провайдера, смене короткого радиоадреса или замене устройства совместимым проверенным преемником.

Внешние идентификаторы являются bindings, а не псевдонимами `asset_id`:

| Провайдер интеграции | Пример внешней привязки | Значение |
| --- | --- | --- |
| Home Assistant | `climate.room_204` | Сущность, опубликованная одним экземпляром HA. |
| Zigbee2MQTT | `room204_sensor` | Имя устройства на уровне интеграции. |
| BACnet | `128 / analog-input:7` | Адрес устройства/объекта. |
| API производителя | UUID ресурса производителя | Удалённая идентичность, специфичная для провайдера. |

Каждая привязка фиксирует провайдера, внешний идентификатор, поддерживаемые возможности, роль управления, первую/последнюю проверку, работоспособность и происхождение. Провайдер может стать недоступным, не стирая актив, его аудит, политики или отношения.

## Контракт возможности

Домен работает с документированными возможностями, а не с протоколами. Начальные примеры: `TemperatureMeasurement`, `OccupancyDetection`, `LightingControl`, `HVACControl`, `DoorControl`, `EnergyMeasurement` и `BatteryHealth`. Контракт возможности называет поддерживаемые наблюдения, команды, единицы, свежесть состояния, семантику качества, состояния ошибок, класс авторизации и доказательство завершения команды.

Физический актив может предоставлять несколько возможностей. Несколько активов могут предоставлять одну возможность для пространства. Особенности провайдера остаются доступны через ограниченный диагностический интерфейс, пока их намеренно не включат в общий контракт возможности. Это не даёт общей модели случайно стать копией Zigbee clusters, MQTT payloads, сущностей Home Assistant или API производителя.

## Несколько привязок и роли управления

Несколько привязок являются нормой, если для развёртывания нужны разные пути управления, наблюдаемости, удобства UI и восстановления при сбое. Запись актива назначает явную роль, а не неявное предпочтение:

| Роль | Пример | Правило |
| --- | --- | --- |
| Основное управление | Команда HVAC через BACnet | Выбирается утверждённым execution plan. |
| Наблюдаемость | Телеметрия Home Assistant | Может информировать контекст и UI, но сама по себе не доказывает завершение команды. |
| Удобство UI | Dashboard Home Assistant | Не может обходить policy OSIP для управляемых действий. |
| Критический резервный путь | Локальный прямой провайдер | Используется только при документированных условиях политики и работоспособности. |

Выбор привязки выполняется планированием исполнения в области действия политики. Он никогда не выводится только потому, что провайдер был обнаружен первым или сообщает самое свежее значение.

## Commissioning и жизненный цикл

Обнаружение создаёт кандидат endpoint провайдера. Ввод в эксплуатацию связывает его с активом только после того, как инсталлятор подтвердит физическое размещение, сопоставление возможностей, класс безопасности и ожидаемую роль управления/наблюдения. Активация делает привязку доступной для политики. Обслуживание, замена, отключение и вывод из эксплуатации — это аудируемые изменения жизненного цикла. Замена сохраняет идентичность актива только после проверки совместимости и физической установки; иначе создаётся новая идентичность актива и документируется связь с выведенным из эксплуатации активом.

## Инварианты

- Идентификаторы объекта и актива — стабильные идентификаторы OSIP, а не преобразованные ID провайдера.
- Исходный payload провайдера не может создать или изменить авторитетную физическую связь без проверенного изменения ввода в эксплуатацию/конфигурации.
- Актив может быть представлен несколькими привязками; ни одна привязка не считается источником истины для каждой возможности.
- Каждая команда и наблюдение атрибутируются активу, возможности, привязке провайдера и области объекта.
- Пользовательское приложение может адресовать пространство, актив, возможность или намерение, но не обязано знать идентификатор базового провайдера.
